Case study: Climbing fflib

This site shows an AI agent improving the Apex code of fflib-apex-common, a widely used Salesforce library. The agent tries one small change at a time. Each change is scored in a Salesforce scratch org on tests, code coverage, static analysis and governor limit use, and is kept only if the score goes up. One such run on a group of classes is called an ascent. The tooling is Climber, and each ascent's code is on its own branch of this fork.

The library was climbed twice: once with Salesforce Code Analyzer's default PMD rules, and once with the PMD brace rules turned off. Comparing the two sets shows how far two independent runs find the same improvements.

How to use this site:

  1. Explore the map below to see how the library is grouped and how each group scored before any ascent.
  2. Explore the ascents for each group. Each ascent's report shows every change the agent tried and why it was kept or discarded, and its retrospective sums up the behaviour changes and patterns.
  3. Compare the out of the box map and its ascents with the map adjusted for style and its ascents, and read what the two sets taught us about Climber.
  4. Read the summary of what all the ascents taught us, both about fflib itself and about how to climb better.

Highlights for the fflib authors (read the fflib findings):

  • Dead code in fflib_SObjectDescribe.
  • Four performance wins that need no caching.
  • An equals without a matching hashCode in fflib_QueryFactory, found by both sets of ascents.
  • An extension point in fflib_StringBuilder that is easy to break, found by both sets of ascents.
  • 198 of the 229 PMD findings are brace rules, which are false positives for fflib because its code style leaves out braces on one-line bodies. That is why the library was climbed a second time with those rules turned off. Without them, six of the ten groups already have a clean PMD score.

Caveats:

  • PMD ran with Salesforce Code Analyzer's default rules and settings. fflib often leaves out braces, which is a valid style choice, and PMD can be configured not to flag it. The map adjusted for style shows the scores without the brace rules.
  • The headroom tests that measure performance were written for these climbs and are not part of fflib. They repeat the same input many times, so the performance findings reflect those tests, not real workloads.
  • Each ascent ran in one scratch org, and the governor limit headroom score varies by about ±12 between runs, so small performance differences are within noise.
  • No anchoring was done. Anchoring means adding tests that fix the expected behaviour before the agent changes the code. We are not fflib's maintainers or authors, so we did not presume what the correct behaviour or the right tests are.
  • The scratch org had multi-currency enabled and no namespace, so behaviour in namespaced orgs was not tested.
  • Every ascent used Claude models to plan, make and review the changes. A model has its own biases, so some of the agreement between the two sets may come from the model, not the code. A future set climbed with a different model of similar capability would test this, and the Venn diagram could then be drawn again with that set.

What the two sets taught us about Climber

Climber's goal is to find the best improvements and bug fixes reliably, so two runs on the same code should find the same ideas. The chart counts the distinct ideas kept by each set across all ten groups, leaving out brace fixes.

  • Both sets kept the biggest performance win in every group, and the main static analysis fixes such as the Graph Engine null check and deferred describes.
  • They agree on about a third of all kept ideas (22 of 68). Counting the 15 ideas that one set kept and the other tried and discarded, they agree on about half.
  • Most disagreement comes from the keep decision, not from missed ideas. Limit headroom varies by about ±12 between runs against a margin of about 5, so the same change can be kept in one run and discarded in another.
  • Longer ascents drift into work of little value. About half of the ideas only the out of the box set kept restructure code to raise line coverage without improving it. That set ran 146 iterations against 75.
  • The sets often agree on what to fix but not how. Five shared findings were fixed differently, such as suppressing a PMD warning in one set and deleting the code it flags in the other.
  • Retrospectives agree more than code changes do. The paired retrospectives share 49 findings, such as stale caches under System.runAs and bypassed virtual hooks.
  • Brace fixes made up most of the out of the box score gains, yet removing them changed little else: the gains outside PMD were similar in both sets.
  • Each set has one run per group, and the ideas were matched by reading the ascent histories, so treat these numbers as approximate.

The same code, scored from the same test and analyzer run as the map above, but with PMD run without the four brace rules (IfStmtsMustUseBraces, IfElseStmtsMustUseBraces, ForLoopsMustUseBraces, WhileLoopsMustUseBraces), which flag fflib's choice to leave braces out of one-line bodies.
