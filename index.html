Climbing fflib-apex-common

This site shows an AI agent improving the Apex code of fflib-apex-common, a widely used Salesforce library. The agent tries one small change at a time. Each change is scored in a Salesforce scratch org on tests, code coverage, static analysis and governor limit use, and is kept only if the score goes up. One such run on a group of classes is called an ascent. The tooling is Climber, and each ascent's code is on its own branch of this fork.

How to use this site:

  1. Explore the map below to see how the library is grouped and how each group scored before any ascent.
  2. Explore the ascents for each group. Each ascent's report shows every change the agent tried and why it was kept or discarded, and its retrospective sums up the behaviour changes and patterns.
  3. To do: compare the out of the box map and its ascents with the map adjusted for style and its ascents.
  4. Read the summary of what all the ascents taught us, both about fflib itself and about how to climb better.

Highlights for the fflib authors (read the fflib findings):

  • Every class reached a clean PMD score with brace and style fixes alone.
  • Dead code in fflib_SObjectDescribe.
  • Four performance wins that need no caching.
  • An equals without a matching hashCode in fflib_QueryFactory.
  • An extension point in fflib_StringBuilder that is easy to break.

Caveats:

  • PMD ran with Salesforce Code Analyzer's default rules and settings. fflib often leaves out braces, which is a valid style choice, and PMD can be configured not to flag it. The map adjusted for style shows the scores without the brace rules.
  • The headroom tests that measure performance were written for these climbs and are not part of fflib. They repeat the same input many times, so the performance findings reflect those tests, not real workloads.
  • Each ascent ran in one scratch org, and the governor limit headroom score varies by about ±12 between runs, so small performance differences are within noise.
  • No anchoring was done. Anchoring means adding tests that fix the expected behaviour before the agent changes the code. We are not fflib's maintainers or authors, so we did not presume what the correct behaviour or the right tests are.
  • The scratch org had multi-currency enabled and no namespace, so behaviour in namespaced orgs was not tested.

If you are a coding agent, use the retrospective JSON files: one per ascent, linked in the table, or all of them in retros.json.

Map adjusted for style

The same code, scored from the same test and analyzer run as the map above, but with PMD run without the four brace rules (IfStmtsMustUseBraces, IfElseStmtsMustUseBraces, ForLoopsMustUseBraces, WhileLoopsMustUseBraces), which flag fflib's choice to leave braces out of one-line bodies. This removes 198 of the 229 PMD violations. Six of the ten groups reach a PMD score of 100.
