Highlights for the fflib authors (read the fflib findings):

  1. An equals without a matching hashCode in fflib_QueryFactory, found by both sets of ascents.
    Two factories that are equal can have different hash codes, so a Set or Map can hold both. The test deterministic_toSOQL relies on this: it puts two equal, empty factories in a Set and expects both to stay. A plain fix is hard because a factory changes after it is built, so a hash based on its query would change while it sits in a collection. The options are to drop the equals override or to document that factories must not be used as keys. The agent only suppressed the PMD warning.
  2. A list search in fflib_Objects where a Set lookup would do.
    containsAll(Set) and containsNot(Set) search the whole object list once for every value they check, so the cost grows with the list size times the number of values. Building a Set from the list once per call makes each check a hash lookup. This is the one performance win whose benefit grows with the input, not just with the repeated input of a headroom test.
  3. An extension point in fflib_StringBuilder that is easy to break, found by both sets of ascents.
    The constructors, including those of FieldListBuilder, call the public virtual add(String), so a subclass that overrides add sees every value. Nothing documents or tests that contract, and the kept change that called buffer.add directly broke it with every test still passing. The comment "Create a distinct set of fields" is also wrong: nothing removes duplicates, so a field listed both directly and in a field set is selected twice. The tests compare the output as a Set, so they check neither duplicates nor order.
  4. A field level security check in fflib_SecurityUtils that fails with a bare NullPointerException on an unknown field name, found by both sets of ascents.
    checkFieldIsReadable, checkFieldIsInsertable and checkFieldIsUpdateable look a field name up with fflib_SObjectDescribe.getField and call getDescribe() on the result without a null check. A name the object does not have, such as a typo or a field that only exists in some orgs, throws "Attempt to de-reference a null object" without naming the field. Throwing an exception that names the object and field would make the failure clear. Verified in a scratch org with Opportunity.LastSyncTime and Account.NoSuchField__c.
  5. Three smaller performance wins that need no caching.
    • fflib_SObjectDomain.getChangedRecords reads the lazy ExistingRecords getter three times per record and reads the Id with a dynamic get('Id'). Reading the map once before the loop and using record.Id removes that per-record work.
    • fflib_SObjectUnitOfWork resolves relationships in the update pass for every type, including types with no dirty records whose relationships were already resolved before insert. Skipping those types saves a second pass over every relationship.
    • fflib_SObjectDescribe builds its cache key with String.valueOf(token).toLowerCase() on every lookup by token, where the SObjectType token itself would work as the key. The kept change also made lookups by name slower, so only the keying is worth taking.
  6. Dead code in fflib_SObjectDescribe.
    The private abstract class NamespacedAttributeMap has a no-argument constructor and a one-argument getObject that neither subclass calls, and getDescribe(String) has a branch that assigns null to a variable that is already null. This is cleanup, not a defect: removing it changes no behaviour.
  7. 198 of the 229 PMD findings are brace rules, which are false positives for fflib because its code style leaves out braces on one-line bodies. The second set of ascents left those rules out. Without them, six of the ten groups already have a clean PMD score.
